# Design

## Context

The pipeline the evals must exercise exists as separate modules: `extractReadableText` and `readPageMetadata` (a page's text and head), the chunker, `buildFactExtractionMessages`, `createOllamaGenerator` (takes a `fetchResource`), `readFactAnswer`, the grounding check and `isImplausibleSubject` in `runFactExtractionJob`, `buildProductFacts`, `resolveConceptKeys`, the table (`buildCell`, `proposeColumns`), `readProductCards`, `selectSummaryFacts`, `buildSummaryMessages` and the statements check. `runFactExtractionJob` is written against IndexedDB, so the runner calls its parts, not the job. `jsdom`, `tsx`, `vitest` and `@mozilla/readability` are already dev dependencies.

## Goals / Non-Goals

**Goals:** repeatable numbers for a prompt, a model and the universality claim; cheap to add a page; no effect on `verify` or the shipped extension.

**Non-Goals:** a pass/fail gate in CI (a 4B model's output varies; a gate would flap); judging statement prose with another model; embedding-model comparison beyond what concept merging uses; storing results in the repository other than the baseline.

## Decisions

### 1. A fixture is the page's HTML and its labels

`evals/fixtures/<id>/page.html` is the page as fetched, `meta.json` its URL and the day it was saved, `labels.json` the expectations:

```json
{
  "facts": [
    { "subject": "Pixel 10a", "concept": "battery capacity", "value": "5100", "unit": "mAh" }
  ],
  "sameConcept": [["battery capacity", "battery size"]],
  "differentConcept": [["screen size", "screen resolution"]],
  "products": ["Pixel 10a"]
}
```

Keeping the HTML, not a text extract, means the evals follow the extractor and the metadata reader as they change. Labels are short and written by hand — what a person would take from the page — not generated by a model. A labelled fact counts as found when some fact kept from the page has the same numbers (or, for a value with no number, the same words), however the unit and the words around it are written; the concept in the label documents what it is and is scored through the concept pairs, because the model's wording of a concept varies.

### 2. The page is read as the extension reads it

The runner loads `page.html` into jsdom and calls the same `extractReadableText` and `readPageMetadata` the content script uses, so what the model sees is what a browser session would send, including the page context block and the product facts from the page's JSON-LD. Nothing is shortcut: chunking, grounding and the subject filter run as in `runFactExtractionJob`.

### 3. Entities, tables and summaries over all the fixtures together

Fixtures are run as one session, so the table, the cards and the summary are built over every page: concept merging across pages and languages is what is being measured. Facts about the same thing are grouped by the normalised name of their subject (the extension's entity resolution would also join names that only mean the same, so a product may appear twice). Concept merging uses the embedding model `nomic-embed-text` by default, as a session with the setup page's models does; `EVAL_EMBEDDING_MODEL=none` turns it off and another name replaces it.

### 4. Metrics

Per run, over the fixtures: the share of extraction answers that could not be read and of those cut off by the token limit (the extension drops a whole chunk for an unreadable answer), junk-subject rate (facts dropped by `isImplausibleSubject` over facts answered), grounded rate, label recall (labelled facts found), concept-merge recall and precision (`sameConcept` pairs merged by the column keys; `differentConcept` pairs kept apart), the share of summary statements that name a product, the number of cards and, in the report, each card's key specs. Time and the number of requests are recorded to compare models, not judged; the model does not report token counts.

### 5. A report and a baseline, no gate

`npm run eval` writes `evals/reports/<time>.json` (ignored by git) and prints a table with each metric beside its value in `evals/baseline.json`. `--update-baseline` rewrites the baseline. The exit code is 0 unless the runner could not run (no Ollama, a missing model, a fixture without labels). Variation is real: `EVAL_RUNS` (default 1) repeats and reports the mean; each run's own numbers are in the report file. `npm run eval:baseline` is the explicit act that rewrites the baseline.

### 6. Outside the shipped code, and outside verify

`evals/` is not under `src/`, is not bundled, and `vitest.config.ts` collects only `src` and `e2e`, so `npm run test` never sees it. `vitest.config.ts` collects `evals/**/*.spec.ts` for the helpers' unit tests, and `vitest.eval.config.ts` collects `evals/**/*.eval.ts` in a jsdom environment (the page is parsed with `DOMParser`, so no extra dependency) with a long timeout. Types in `evals/` are checked by `npm run typecheck`, and the runner's own pure helpers (matching labels, computing metrics, formatting the table) carry unit tests that run in `npm run test` with the rest.

### 7. Capturing a page

`npm run eval:capture -- <url> <id>` fetches the URL with a plain request and a browser-like `User-Agent`, writes `page.html` and `meta.json`, and creates an empty `labels.json` template for the developer to fill. It refuses an `<id>` that exists. It runs on the developer's machine; the extension never does.

### 8. What the runner imports

The runner uses the feature barrels. Two helpers that the job kept private (`isImplausibleSubject`, `buildProductFacts`) move from `runFactExtractionJob/utils/` up to `factExtraction/model/`, since a second consumer now uses them, and join the barrel with a few constants and `readProductCards`/`readSummaryAnswer` of `clusterSummaries`. `readPageMetadata` and `extractReadableText` stay out of the barrels, as before, and are imported by path, the way the content script does.

## Risks / Trade-offs

- **Variation in a small model's output.** Without a gate there is no flapping; the baseline and the range show a real change from noise only for large changes. Mitigation: `EVAL_RUNS`.
- **Few pages, few conclusions.** Five pages do not make a benchmark; they make a regression net and a way to compare two prompts on the same input. The set is meant to grow by capture.
- **Pages change or go away.** Saved HTML does not; the labels are tied to it.
- **Copyright and personal data in the repository.** Shop pages are public but not ours. Mitigation: fixtures are the developer's choice, may be kept out of git (`evals/fixtures/` ignorable per fixture), and a fixture records its source URL and day.
- **The runner can drift from the background's pipeline.** It composes the modules by hand. Mitigation: it imports the same modules, and the design keeps the composition in one file that reads like `runFactExtractionJob`.

## Migration Plan

Nothing runs on upgrade. A new directory and scripts; delete them to roll back.

## Open Questions

- **Which five pages?** The pages of the "Iphone" session on `jabko.ua` that the earlier work was tuned on, plus at least two that are not electronics and one that is not in Ukrainian or English-speaking shops' markup (a pen, a bath mat). The developer names the URLs; this change cannot choose them.
- Should fixtures be committed? Default: committed, so the baseline means the same on every machine. If copyright is a concern, keep them local and commit only `labels.json` and the baseline; the runner then skips fixtures whose HTML is absent and says so.
